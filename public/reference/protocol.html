OBX Protocol (read side) (0.1.0)

Download OpenAPI specification:

URL: https://openbrandexchange.com License: CC-BY-4.0

How retailers' software discovers a brand node, gets access and pulls product content.

Normative. The Open Brand Exchange (OBX) Protocol is the read side of a brand node: a retailer's software (shop, PIM, ERP, content hub) discovers the node, requests access, authenticates with OAuth2 client credentials and pulls brands, products, variants (with GTIN) and final images with role, view, order, rights and AI provenance.

The prose specification in docs/protocol.md is authoritative where this file is silent. Key words MUST, SHOULD, MAY are to be interpreted as described in RFC 2119.

Conventions for every endpoint:

  • JSON is UTF-8, field names are snake_case, timestamps are RFC 3339.
  • Clients MUST ignore unknown fields, unknown enum values and unknown change types. Extension fields are prefixed x-<vendor>- (for example x-acme-crop).
  • Errors are application/problem+json (RFC 9457) with an obx_error code, except the OAuth2 token endpoint which uses RFC 6749 error JSON.
  • Responses carry OBX-Version: 0.1 and rate limit headers (RateLimit-Limit, RateLimit-Remaining, RateLimit-Reset); 429 carries Retry-After.
  • A retailer never sees more than it could see in the brand's portal: only published objects of brands in its grant.

Access

Request access and obtain tokens.

Request access (unauthenticated)

Creates a retailer access request that the brand approves or rejects in its admin. Unauthenticated and rate limited (RECOMMENDED: 5 per hour per IP). The response is the same whether or not the brand already knows the retailer (no enumeration). Nodes whose brand disabled requests answer 403 forbidden.

Authenticated with the request_token from the 202 response as Bearer token. After approval with API access the response contains credentials with the client_secret exactly once (first read); later reads return client_secret: null and claimed: true. Poll at most once per minute.

OAuth2 token endpoint (client credentials)

RFC 6749 section 4.4. Nodes MUST support client_secret_basic and MAY support client_secret_post. scope is optional; when absent all scopes of the client are granted. Requesting a scope the client does not have yields invalid_scope. A revoked client or blocked retailer yields invalid_client. Access tokens SHOULD live 3600 s; there are no refresh tokens (request a new token).

Keyset-paginated, ordered by id ascending. For synchronisation use /changes; this endpoint is for browsing and targeted reads. Objects outside the caller's grant are never returned (unknown ids in ids are silently omitted).

Changes

The change feed, the heart of synchronisation.

Change feed

Without cursor the node starts a snapshot: one upsert per currently visible object (brands, then products, then variants, then assets), phase: snapshot; then the feed switches to phase: live at the sequence number where the snapshot started. With a cursor it returns entries after it. Pages never mix phases; the last snapshot page has has_more: true.

Entries are at-least-once: the same object may appear several times, data is always the CURRENT representation. Deletes are tombstones for anything no longer visible to the caller. Tombstones are kept at least 90 days; an older cursor yields 410 cursor_expired (restart without cursor). A grant entry with resync: true means restart without a cursor. next_cursor is always returned; poll again later (RECOMMENDED: not more often than every 60 s when has_more is false, or on a changes.available webhook).

Webhooks

Event delivery to a consumer's webhook URL Webhook

Sent by the node to each active subscription. Headers: OBX-Webhook-Id (event id), OBX-Webhook-Timestamp (unix seconds), OBX-Webhook-Signature: v1=<hex> where hex = HMAC-SHA256(secret, <timestamp>.<raw body>). Receivers MUST verify in constant time and reject timestamps more than 300 s away. Respond 2xx within 10 s; otherwise the node retries with exponential backoff for up to 24 h.
